# J1202 — LincheckFailure

**Tier:** T5 (lincheck) · **Default level:** deny

## Why it matters

Lincheck explores the interleavings of a class's `@Operation` methods and replays them against a
sequential specification of the same class. A failure means some concurrent execution produced a
result no sequential execution could: the class is not linearizable, so its behaviour depends on
timing. That is the same class of bug jcstress finds (J1201), but Lincheck reports the exact
interleaving and a linearizability witness instead of a raw forbidden state.

## Failing example

```java
public class RacyCounter {
    private int value;

    @Operation
    public int increment() {
        return ++value; // read-modify-write, not atomic
    }

    @Operation
    public int get() {
        return value;
    }
}
```

Lincheck reports `Invalid execution results`: two increments that both return `1`.

## Fixed example

```java
public class SafeCounter {
    private final AtomicInteger value = new AtomicInteger();

    @Operation
    public int increment() {
        return value.incrementAndGet();
    }

    @Operation
    public int get() {
        return value.get();
    }
}
```

## Notes

- `jcheck lincheck` resolves `org.jetbrains.kotlinx:lincheck-jvm` (the `lincheck` artifact is an
  empty Kotlin-multiplatform stub), compiles the project's Java test sources when the build tool has
  not, and runs every class that declares an `@Operation` method.
- Kotlin Lincheck tests are supported once the project's own build has compiled them — javac cannot
  read Kotlin sources, so run `jcheck build` first.
- Modes: `[tests] lincheck_mode = "model-checking"` (default) explores interleavings
  systematically; `"stress"` runs randomized concurrent invocations. `lincheck_iterations` bounds
  both.
- The report headline becomes the diagnostic message; the full report stays in the run log, because
  a rendered diagnostic cannot carry Lincheck's tables.
- Lincheck 2.39's bundled ASM reads class files up to Java 22 (major version 66), and its
  instrumentation silently does nothing when it cannot read the bytecode — which would turn a racy
  class into a clean pass. jcheck therefore compiles the project's Java Lincheck test sources at
  `min([project] release, 22)` and says so when it clamps the release, and it *refuses* a
  pre-compiled test class newer than that (a note plus a tool-failure exit) instead of reporting a
  pass it could not verify.
- Lincheck needs a JVM that can attach its instrumentation agent; a JVM started with
  `-XX:+DisableAttachMechanism` cannot run it.
