# J1101 — MutantSurvived

**Tier:** T5 (mutation testing) · **Default level:** warn

## Why it matters

A green test suite is only as meaningful as its assertions. PIT mutates the compiled code — flips a
conditional, changes a boundary, removes a call — and re-runs the tests. A mutant that survives
means no test's result depends on that piece of logic, so the code could be wrong and the suite
would still pass. This is the highest-signal check jcheck runs, and the slowest, so it is opt-in
and scoped to the files you name.

## Failing example

```java
static int abs(int x) {
    return x < 0 ? -x : x;
}
```

```java
@Test
void positive() {
    assertEquals(3, abs(3)); // never exercises the negative branch
}
```

PIT reports `changed conditional boundary` and `negated conditional` as surviving on the `abs`
line: the test would pass even if the negative branch were wrong.

## Fixed example

```java
@Test
void negative() {
    assertEquals(3, abs(-3)); // now the branch is covered and the mutant is killed
}
```

## Notes

- `jcheck mutate` runs PIT and reports each survivor at its line with PIT's description, for
  example `mutant survived: negated conditional`.
- `mutant has no coverage` means no test executed the line at all, which is an even larger hole
  than a weak assertion.
- Scope it to what changed: `jcheck mutate --sources src/main/java/demo/Cart.java` mutates only
  that class. This is what makes it usable in an edit loop.
- PIT needs compiled main and test classes and a JUnit Platform; `jcheck mutate` resolves the
  launcher and puts the project's JUnit ahead of PIT's own so a version clash cannot hide the
  result. Set `[tests] mutation_testing = true` for `jcheck test` to run it too.
