# J1301 — AddOverride

**Tier:** T3 (jcheck-checks) · **Default level:** warn

## Why it matters

`@Override` is the compiler's cheapest safety net. Without it, renaming or mistyping a method that
was meant to override a supertype method produces a new method that is never called, and the
compiler says nothing. With it, the same change fails to compile. Error Prone's `MissingOverride`
covers this when Error Prone is attached; jcheck ships its own so the fix is available without it,
and `jcheck fix` applies it.

## Failing example

```java
interface Greeter {
    String greet(String name);
}

final class GreeterImpl implements Greeter {
    public String greet(String name) { // no @Override: a rename would silently stop working
        return "hi " + name;
    }
}
```

## Fixed example

```java
interface Greeter {
    String greet(String name);
}

final class GreeterImpl implements Greeter {
    @Override
    public String greet(String name) {
        return "hi " + name;
    }
}
```

## Notes

- The check uses the compiler's own `Elements.overrides`, so it reports a method that overrides a
  superclass method, implements an interface method, or redeclares a generic signature correctly —
  not a textual lookalike.
- Static, private and constructor declarations cannot override anything and are not reported.
- The fix is machine-applicable: `jcheck fix` inserts `@Override` on its own line, matching the
  method's indentation.
- Suppress with `@SuppressJcheck(code = "J1301", reason = "...")` only where the annotation is
  genuinely impossible, which in ordinary Java it is not.
